# MASAI AI/ML Capstone Project
# Delhivery Last-Mile Delay Intelligence Pipeline

This project builds a last-mile delay intelligence pipeline for Delhivery-style parcel operations. It starts with messy shipment data, cleans and engineers the features, estimates delivery time, predicts late parcels before they miss their promise, segments hubs by risk, and converts the final model into an ops-ready action list for new shipments.

## How to run

From a fresh clone, run these commands in order:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python generate_data.py
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

Important: `models/delay_model.pkl` is regenerated by `python package_model.py`. The committed pickle is only reliable when the installed scikit-learn version matches the pinned version in `requirements.txt`. If versions differ, the grader re-runs `package_model.py` instead of loading the stored pickle.

## Data findings

- Service type: Express had the highest delay rate at 0.4897, compared with Standard at 0.2056 and Economy at 0.0857.
- Hub tier: delay rate rose from 0.0400 in Tier 1 to 0.4400 in Tier 3.
- Distance band: delay rate increased from 0.0219 in the 0-200 km band to 0.8523 in the 601+ km band.
- The strongest correlations with `delivery_hours` were `promised_hours` (+0.8372), `distance_km` (+0.4013), and `n_stops` (+0.3247), ranked by absolute correlation in `outputs/part_a_correlations.csv` after excluding `delivery_hours` itself.
- `declared_value_inr` was log-transformed because the filled column was highly right-skewed: the raw mean and median were 1533.0542 and 1121.5000, while the log-transformed mean and median were 7.0277 and 7.0224, which is much more stable for modeling.

## Model results (regression)

- Baseline validation R² was -0.0212. That means the constant-mean benchmark was worse than a flat line at the mean, so it was not useful for planning.
- The best validation model was `linear_regression`, with RMSE 4.8912 hours. `gradient_boosting` was very close at 4.9165 hours.
- Tree-depth analysis showed high bias at shallow depths: depth 1 had train RMSE 11.6334 and validation RMSE 12.1324, with a small gap of 0.4989. The clear overfitting regime appeared at unlimited depth, where train RMSE fell to 0.0000 and validation RMSE rose to 7.7890, giving a gap of 7.7890.
- The best learning rate was 0.1. It produced validation R² 0.9306. A rate of 0.01 was too slow and underfit (R² 0.7127), while 1.0 was too aggressive and overshot (R² 0.8440).
- Cross-validation disagreed with the single validation split: `gradient_boosting` had mean R² 0.9352 versus `linear_regression` at 0.9261. If asked to pick one model, I would still ship `gradient_boosting` because its CV signal was stronger and more stable, even though `linear_regression` won the one validation split by a small margin.

## Model results (classification)

- Blind baseline: predicting every parcel as “not delayed” achieved accuracy 0.7667, but it had precision 0.0000, recall 0.0000, and F1 0.0000. It looked good on accuracy alone, but it missed every delayed parcel.
- Noise columns: the five noise columns contributed a combined random-forest importance share of 0.2282. All five were outside the top 7 by F-score, so they did not carry strong delay signal.
- Feature selection was strongest at `k = 7`, which gave validation F1 0.8333. The other tested values were worse: `k = 5` gave 0.6988, `k = 10` gave 0.7857, `k = 12` gave 0.8148, and `k = 17` gave 0.8101.
- Tuning did not beat the untuned forest on validation. The untuned forest at `k = 7` had F1 0.8333, while grid search reached 0.7750 and randomized search reached 0.7848. On a 180-row validation slice, the tuning differences were small enough that over-optimization added noise rather than signal.
- The final alert threshold was 0.5. This was the highest threshold that still kept validation recall at or above 0.80 while preserving useful precision. At 0.5, precision was 0.7955, recall was 0.8333, and F1 was 0.8140. Lowering to 0.1 improved recall to 0.9762 but cut precision to 0.4824; raising to 0.6 improved precision to 0.8889 but lowered recall to 0.7619.
- On the held-out test set, the final model reached precision 0.6889, recall 0.7561, and F1 0.7209. Test recall was lower than validation recall (0.7561 vs 0.8333), which is expected because the test set had only 41 delayed parcels and a few misses move the metric noticeably.

## Operations recommendation

- The highest-risk segment was `Escalate`, with 9 hubs and a delay rate of 0.46.
- Tier labels were not always reliable. The mismatches were `HUB07` (Tier 1, Watch), `HUB13` (Tier 2, Escalate), `HUB15` (Tier 2, Escalate), and `HUB22` (Tier 3, Watch). This shows that tier is useful context, but segment-based risk triage should drive action.
- The production alert threshold is 0.5. At that level, the model recovered 0.7561 of delayed parcels and correctly classified 0.6889 of flagged parcels on the test set.
- On the 48 new shipment records, 8 were flagged and 6 of those 8 were escalated to a hub manager; the other 2 flagged parcels were sent to proactive customer calls.
- I kept `K = 3` for segmentation because the across-to-within ratio was 5.3928 with cluster sizes 9-8-7. `K = 2` was too coarse, while `K = 4` and `K = 5` split the network into small clusters that were harder to manage operationally and did not materially improve the structure.

## Production plan

(a) Production-readiness checklist:
- Accuracy: model quality is tracked in `outputs/part_c_final_test.csv` and `outputs/part_c_models.csv`.
- Reliability: `package_model.py` saves the final pipeline and verifies that the reloaded model gives the same probabilities on the test rows.
- Reproducibility: `requirements.txt` pins the exact Python library versions, and the same preprocessing path is used for training and prediction.
- Performance: the final pipeline is compact and fast enough for batch or near-real-time scores.
- Maintainability: feature engineering is centralized in `src/shipment_prep.py`.
- Consistency: `predict_delay.py` uses the same cleaning and feature-order logic as the training pipeline.
- Monitorability: the repo records threshold checks, model checks, and action outputs.

(b) What to monitor with triggers:
- Weekly delayed share of delivered parcels: trigger if it rises above 0.25.
- Weekly share of flagged parcels: trigger if it rises above 0.12.
- Recall on parcels whose outcomes are now known: trigger if it falls below 0.75.
- Precision on scored parcels: trigger if it falls below 0.60.

(c) Retraining and sale-window handling:
- Retrain monthly, and also after any major network change or campaign burst.
- For the 15-28 September sale window, compare against the same type of event window, not against normal weeks, because `sale_event_flag` materially changes shipment risk.
- Drift would show up as a sustained rise in delay rate, flagged share, hub-segment drift toward `Escalate`, or a systematic change in median distance, stops, or delay rate versus the previous comparable period.

## Limitations

- The data are synthetic, so the model learns a generated operating pattern rather than a live logistics network.
- The test set is small for class imbalance: only 41 delayed parcels were present in the test split.
- The alert threshold was tuned on a single validation split, so it is sensitive to the exact random split.
- The action policy uses one model and one threshold without a formal cost model for false alarms versus missed escalations.
- Segment assignments are based on historical cohorts and may drift during severe weather, route disruption, or unusual demand spikes.
